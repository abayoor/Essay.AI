# EssayCoach — мастер-спецификация проекта

Этот файл перенесён из исходной мастер-спецификации и адаптирован к уже готовому стартовому стеку проекта. Он остаётся источником задач между сессиями Codex.

## 1. О продукте

EssayCoach — русско-казахско-английская платформа для абитуриентов из Центральной Азии, которые готовят заявки в зарубежные университеты, на гранты и стипендии.

Главное отличие: это **коуч, а не гострайтер**. Приёмные комиссии замечают слишком гладкие и обезличенные эссе. Поэтому продукт помогает ученику находить собственные детали, структурировать черновик и задаёт вопросы, но никогда не создаёт финальное эссе вместо него.

## 2. Неподвижные этические правила

- ИИ не пишет и не переписывает готовое эссе целиком.
- На прямую просьбу «напиши за меня» ИИ вежливо отказывает и предлагает три конкретных наводящих вопроса.
- Предложения ИИ отображаются отдельно от текста ученика: в панели или в заметках на полях.
- Нельзя хранить полные тексты чужих эссе без явного согласия правообладателя.
- В будущей библиотеке допускаются только официальные ссылки, обезличенные материалы пользователей с отзываемым согласием и разборы техник без копирования текста.

Текст для будущей формы согласия: «Поздравляем с поступлением! Хочешь помочь будущим абитуриентам? Если согласишься поделиться своим эссе (обезличенно, без имени и точных деталей, по которым тебя можно узнать), мы добавим разбор твоей техники в библиотеку — не сам текст целиком, а то, что в нём сработало. Ты можешь отозвать согласие в любой момент в настройках».

## 3. Технический контекст этого репозитория

Исходная версия документа предлагает Next.js и Claude. Этот репозиторий уже построен на Vite + React 18 + TypeScript + wouter + Supabase + Vercel, поэтому стек не меняем. ИИ вызывается только через существующую Supabase Edge Function ai, которая использует Gemini и секрет GEMINI_API_KEY.

- Данные и авторизация: только Supabase.
- Любая схема БД: миграция в supabase/migrations, затем команда db:push.
- Для каждой таблицы с пользовательскими данными обязательны RLS и политики «пользователь видит только свои записи».
- Ключи живут только в .env и Vercel; service_role не используется.
- Полноценные экраны — в src/pages, компоненты — в src/components, запросы к БД — в src/lib.

## 4. Первая фаза (MVP)

Цель — рабочий продукт для первых пользователей за 1–2 недели.

1. Авторизация Supabase: email/password (пароль от 8 символов) и Google OAuth.
2. Онбординг: язык интерфейса, цель поступления, целевые школы.
3. Dashboard: пустое состояние и список личных эссе.
4. Создание эссе: название, школа, тип заявки.
5. Редактор: текст, счётчик слов, сохранение новой версии каждые 30 секунд и вручную.
6. ИИ-фидбэк: хук, структура, клише, «показывай/рассказывай», голос, статус по словам и лёгкие заметки на полях.
7. Тестирование сценария: регистрация → онбординг → создание → сохранение версии → запрос фидбэка → отображение JSON.

Схема первой фазы: users, prompts, essays, essay_versions, feedback_logs. Триггер создаёт профиль из auth.users; таблицы с данными ученика защищены RLS.

## 5. Промт коуча

Коуч работает с абитуриентами из Казахстана и Центральной Азии. Он даёт честный и конкретный фидбэк по хуку, структуре, «show, don’t tell», голосу и лимиту слов. Нельзя придумывать биографические детали или отдавать готовые абзацы. Ответ возвращается строго JSON с полями:

- hook_feedback
- structure_feedback
- cliche_flags
- show_dont_tell_ratio
- voice_notes
- word_count_status (under, within, over)
- ghostwriting_request
- margin_comments (quote, note)

## 6. Дизайн

Академичный и доверительный: тёмно-синий/графитовый, один тёплый охристый акцент, много воздуха. Заголовки — serif, интерфейс — sans-serif. Комментарии ИИ должны быть лёгкими и поддерживающими, а не похожими на исправления красной ручкой. Мобильная адаптивность обязательна.

## 7. Последующие фазы

**Фаза 2:** база требований университетов, канбан-трекер, брейншторм-анкета, напоминания о дедлайнах.

**Фаза 3:** библиотека паттернов только с законными источниками и подтверждённым согласием, поиск по эмбеддингам, маркетплейс менторов, Stripe и серверный rate limiting дорогих запросов.

## 8. Безопасность

- Секреты — только в окружении.
- Не рендерить пользовательский текст через HTML.
- Проверять и валидировать входные данные.
- Будущие Stripe webhook и cron защищать подписью/секретом.
- Не открывать short_excerpt в библиотеке без permission_verified.
